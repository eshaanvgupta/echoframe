## ERC-8183 compatibility snapshot

Authoritative [ERC-8183 draft](https://eips.ethereum.org/EIPS/eip-8183); source snapshot: [`ethereum/ERCs` commit `a078cab5cc8e9581c15f76c091ed96eed28f02f7`](https://github.com/ethereum/ERCs/blob/a078cab5cc8e9581c15f76c091ed96eed28f02f7/ERCS/erc-8183.md). Draft interfaces may change. Do not assume a standard Celo deployment address.

The status enum, in numeric order, is `Open=0`, `Funded=1`, `Submitted=2`, `Completed=3`, `Rejected=4`, `Expired=5`. Allowed normative transitions are Open→Funded/Rejected, Funded→Submitted/Rejected/Expired, Submitted→Completed/Rejected/Expired. Terminal states cannot transition.

Important upstream inconsistency: normative prose requires funding with an expected budget, whereas the current embedded reference implementation accepts `fund(uint256,bytes)` without that parameter. The prose says client or provider can set a budget; the embedded reference checks provider only. The embedded reference also allows zero-budget Open→Submitted, beyond the normative state diagram. A reader must pin and declare the exact ABI/profile rather than pretend all implementations share one universal ABI. ECHOFRAME must not build payment writes from these ambiguous signatures.

The embedded reference's read interfaces are:

```solidity
function paymentToken() external view returns (address);
function getJob(uint256 jobId) external view returns (Job memory);
// Job tuple, in order:
// uint256 id, address client, address provider, address evaluator,
// string description, uint256 budget, uint256 expiredAt,
// uint8 status, address hook
```

`jobs(uint256)` is also an autogenerated public mapping getter, but `getJob` gives an explicit tuple. Treat unsupported selectors, malformed return tuples, missing bytecode and mismatched code hashes as unsupported; do not substitute guessed fields.

Reference event signatures (indexing affects decoding but not the topic hash):

| Event | Indexed fields | Non-indexed fields |
| --- | --- | --- |
| `JobCreated(uint256,address,address,address,uint256,address)` | jobId, client, provider | evaluator, expiredAt, hook |
| `ProviderSet(uint256,address)` | jobId, provider | none |
| `BudgetSet(uint256,uint256)` | jobId | amount |
| `JobFunded(uint256,address,uint256)` | jobId, client | amount |
| `JobSubmitted(uint256,address,bytes32)` | jobId, provider | deliverable |
| `JobCompleted(uint256,address,bytes32)` | jobId, evaluator | reason |
| `JobRejected(uint256,address,bytes32)` | jobId, rejector | reason |
| `JobExpired(uint256)` | jobId | none |
| `PaymentReleased(uint256,address,uint256)` | jobId, provider | amount |
| `EvaluatorFeePaid(uint256,address,uint256)` | jobId, evaluator | amount |
| `Refunded(uint256,address,uint256)` | jobId, client | amount |

`JobCreated` prose omits `hook`, which is present in the reference event. Declare support for the reference signature above and reject other layouts unless an explicit configured adapter exists. Require an independently verified configured contract/code profile, exact emitter, topic count, ABI data length, successful containing receipt and selected job ID. Completion establishes that the evaluator finalized escrow; it does not establish independent correctness of the deliverable. The evaluator may be the client or an arbitrary contract. A `bytes32` reason/deliverable binds a commitment, not its truth or quality.

## Optional identity reads

ERC-8004 remains [a draft specification](https://eips.ethereum.org/EIPS/eip-8004). [Celo's official guide](https://docs.celo.org/build/agents/8004) identifies the mainnet Identity Registry at `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` and Reputation Registry at `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63`. The Identity Registry address returned nonempty bytecode in a read-only `eth_getCode` observation (130 bytes, likely proxy code). A nonempty proxy does not independently verify its implementation or trustworthiness. Useful bounded reads include `ownerOf(uint256)`, `tokenURI(uint256)` and `getAgentWallet(uint256)`. Metadata is declarative, may be mutable, and is not proof of paid service delivery. Disable automatic fetching of arbitrary metadata URIs; validate schemes, size, timeout and privacy first. [ERC-8004 best practices](https://github.com/erc-8004/best-practices) guide registration and reputation interpretation.

[Official Self Agent ID repository](https://github.com/selfxyz/self-agent-id) and [Celo guide](https://docs.celo.org/build/agents/self-agent-id) describe human-backed agent identity. Current official SDK network constants snapshot: [`dbb6086a5b9b1700c4586fd894d89bd87dcea17c`](https://github.com/selfxyz/self-agent-id/blob/dbb6086a5b9b1700c4586fd894d89bd87dcea17c/typescript-sdk/src/constants.ts).

| Network | Self registry | Bytecode observation |
| --- | --- | --- |
| Mainnet | `0xaC3DF9ABf80d0F5c020C06B04Cced27763355944` | 135 nonempty bytes |
| Sepolia | `0x043DaCac8b0771DD5b444bCC88f2f8BBDBEdd379` | 135 nonempty bytes |

Safe narrowly scoped reads: `isVerifiedAgent(bytes32) → bool`, `getAgentId(bytes32) → uint256`, `hasHumanProof(uint256) → bool`, `isProofFresh(uint256) → bool`, `proofExpiresAt(uint256) → uint256`. Require registry chain/profile checks. Do not call credential-disclosure methods, collect passport details, enroll users, request keys, or infer that identity proves quality. Registry constants are configuration sourced from upstream, not an ECHOFRAME claim that identity was enrolled. The Self SDK is BUSL-1.1 at this snapshot; do not copy its implementation into an MIT product. Basic factual ABI/address interoperability can be implemented independently.
