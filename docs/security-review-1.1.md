# Internal engineering security review — 1.1.0

This is an internal code review and regression record, not an external audit, formal verification or demonstrated exploit against a production merchant. Conditions and fixes refer to the repository implementation. No vulnerability in Celo, x402, MPP or ERC standards is inferred from simulated cases.

| Observed implementation gap | Change | Evidence |
| --- | --- | --- |
| Absent payment expectations passed vacuous checks; a sole log was automatically selected | Require exact chain, transaction, asset, sender, recipient, atomic amount, explicit log, trusted expectation origin and configured ERC-20 behavior for positive attribution | `production-security.test.ts`, `celo.test.ts`, browser single-log test |
| Imported financial labels could resemble current verified purchase status | Separate recorded financial statements from current attribution; real imports remain UNKNOWN; expose execution, Transfer observations and reproduced checks independently | Import/provenance tests and UI verdicts |
| Public-minimal exports preserved delivery event names after withholding payloads | Withheld event names do not grant a returned/empty work conclusion | Public export regression |
| JSON.parse silently selected duplicate members; sparse arrays could collide with dense canonical forms; getters/subclasses could run caller code | Reject duplicate decoded member names at JSON boundaries; reject sparse/accessor/subclass arrays, accessors, symbol and non-enumerable object members; restrict commitment domains | Canonical boundary tests, encoded protocol tests |
| Invalid safe-schema definitions in absent branches escaped validation | Validate every schema branch and constraint before evaluation | Unobserved-branch regression |
| A proof could hash selected file bytes while evaluating a different body | Bind body-based checks to equal parsed JSON file bytes; presence on selected files uses byte length | File/body substitution and empty-file presence tests |
| Outcome proof parsing accepted extra unbound root fields | Strict proof/result/signature schemas; exact reproduced result and proof commitment required | Unsupported attestation field regression |
| Accepted attachment sizes and encrypted-file parsing disagreed with portable bundle limits | Permit declared base64 attachment size inside bounded bundles; cap plaintext at 8MB, allow its base64 envelope/tag, validate encryption envelope fields | Large bundled attachment and >8MB encrypted envelope round-trip tests |
| SDK normalization could silently strip unsupported echoed MPP challenge fields or duplicate members inside encoded requests | Validate raw supported fields and decoded nested JSON before official codecs; reject unknown profiles and duplicate receipt/challenge parameters | MPP compatibility/security tests |
| Isolated exchanges lacked durable request/quote/authorization binding | Persistent opaque correlation, quote pinning, authorization fingerprints, journal identity, conservative recovery and explicit response attribution | Actual Express/Hono tests, installed self-test |
| A response observation deadline could be followed by application writes | Finalized observers ignore later writes, retain no incomplete-body digest and release buffered bytes | Actual delayed Express response and direct observer tests |
| Concurrent optional outcomes could target a changing event index | Serialize finalization per context; detect overlapping requests without creating another attempt | Concurrent projection and independent bundle verification regression |
| Receipt inclusion by hash alone did not detect an orphaned block | Also check canonical height/hash/transaction membership; pending receipt contradictions stay UNKNOWN | Reorganization, pending cross-RPC and existing receipt tests |
| Custom RPC endpoint paths/queries, raw exception text or unknown provider receipt extensions could carry credentials into evidence | Export origin-only endpoint labels, sanitize RPC errors and retain supported receipt/log fields only | Provider credential/extension privacy regressions |
| Journal attribution could depend on provider-specific receipt annotations | Stable chain/transaction/log identity; atomic uniqueness across attempts; separate logs stay distinguishable | Two-attempt settlement identity regression |
| Edited studio inputs could leave a stale passing proof displayed | Clear compiled proof/verification when input or policy changes | Browser edit/recompile regression |

Imported evidence is parsed as bounded JSON; no imported scripts, dynamic validators, eval, HTML attachments or decompression are executed. React text and HTML export escape hostile strings. Source signatures use the documented signed bytes; trusted signer identity remains an external decision. Hash integrity detects changes against a known root, not a rewritten unsigned story. Stored RPC records never become consensus proofs.

Recorder raw headers, signatures, nonces, credentials, cookies, request bodies and wallet secrets never enter its persisted request boundary. Default response observation keeps metadata and commitments only. Explicit JSON allowlists apply sensitive-name/known-secret redaction and bounded capture; arbitrary personal information cannot be universally detected. Projection checks do not authenticate hidden original bytes or the recorder. Error messages crossing capture callbacks are sanitized, and incomplete writes reject `drain` rather than pretending success. Complete exports and generated trace tests deliberately include retained evidence and require intentional selection.

SQLite append-only transitions, immutable identities, transactional writes and settlement uniqueness are tested. Recorder state and journal are separate transactions: recovery conservatively links partial records and requests reconciliation. They are local plaintext databases; OS directory/file permissions and device security remain the integrator's responsibility. Export files refuse overwrite and use restrictive permissions where supported. Browser evidence is opt-in IndexedDB; encryption is a portable authenticated AES-GCM export, not automatic database-at-rest encryption. Lost passwords are not recoverable. JavaScript string memory cannot be reliably zeroized.

RPC methods are read-only. Default endpoints are official Forno HTTPS origins; custom origins require trusted application configuration. Imports and MCP cannot supply arbitrary endpoint URLs. Redirects are refused. Response sizes, deadlines and retries are bounded. Explicit application configuration is trusted and can deliberately select another HTTPS origin; it must not be populated from untrusted request input. No processor signatures, facilitator HMACs, token economic behavior, mandate authority, finality or subjective quality are claimed as verified.

The recorder does not enforce merchant payment acceptance and never signs, broadcasts, settles genuine payments, retries, refunds, deploys or registers. Example facilitator settlement endpoints are isolated loopback simulations and accept synthetic credentials. Do not expose them as payment processing. Existing live merchants retain responsibility for the genuine payment stack.

Dependency advisories, licenses, build checks, browser accessibility and performance results are in `release-verification.json` and `artifacts/`. Counts are generated from executed checks. Six redundant browser combinations intentionally run only at desktop; representative interactions run at all four widths. Automated audits and Chromium emulation do not certify real-device accessibility or universal security.

Remaining external validation: a consenting genuine merchant integration, independent developers' feedback/usage, any authorized funded mainnet purchase, publication account access and an external security review if desired. Public mainnet observations do not fulfill those milestones.
